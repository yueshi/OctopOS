结论 · SUMMARY

不做第二套账号系统，也不把 guest 当终态

v3 修正：身份 / 凭证 / 授权三层各只有一个事实源；guest 只能 participate；P1 用 per-app token，不用 cookie。
01 · PRINCIPAL

PrincipalDirectory

member / guest / submission / anonymous 统一解析；底层先用 users.kind，以后可换独立 principal 表，不让业务代码依赖表结构。

02 · MEMBERSHIP

成员 + 表级可见性

应用成员关系决定访问；member_visible 决定 participant 能看哪张表；row_owner 决定哪一行属于谁。三者缺一不可。

03 · AUTHORIZE

先授权矩阵，后身份表

HTTP / Agent / IM 统一走 authorize(principal, app, action, table, row)；PII 按行判定；export/aggregate 是独立 action。

一句话：平台账号决定「谁能进 Octop」，应用成员 + 表级可见性决定「谁能用哪个应用、看哪张表、哪一行」，IM 绑定只决定「这个聊天账号是谁」。 身份、成员、授权三层分开，不能互相推导。

结论 · v3 修正方向
设计修正 · WHAT CHANGED

v2 → v3：八个问题，三条原则

每层单独看都对，合起来互相矛盾；v3 用凭证 scope 把身份 / 凭证 / 授权拆开。
01 · IDENTITY

guest 会话三条约束互斥

per-app 会话、非 app scope 拒绝 guest、/api/guest/apps 跨应用门户不能同时成立；UserManager 缓存还会让 guest app token 直接 401。

修正：新增 guest scope；guest 由 PrincipalDirectory 从 repo 解析，不进平台缓存。

02 · AUTHZ

guest 可持 view，绕过表可见性

v2 让 guest 持有 view / participate；但 view 能读全部表并导出，member_visible 只约束 participant，等于留了一个后门。

修正：guest 只能 participate；view 是平台成员专属；表可见性对所有 participate 生效。

03 · IM

P2a 只封了 share_link，没封数据工具

所有 app 工具仍以 agent owner 鉴权；未绑定的人在 DM 里让 Agent 调 app_read_data，拿到的仍是 owner 视角的个人数据。

修正：P2a 所有 app 数据工具要求 owner_verified；只放行链接 / 打开类工具；/link 建立 guest 的 IM 绑定。

v3 原则：凭证 scope 先于身份表；先授权内核，后成员关系；行归属先于行级 PII；先工具面收口，后 IM actor。

问题 · PROBLEM

四类人，四种缺口

根因不是缺页面，而是缺「应用成员 + 表级可见性 + 主体抽象」。
外

外部参与者

无身份

没有 Octop 账号的同事、客户、供应商。现在只能拿 /p/{token} 公开只读链接。

不能写、不能看自己的提交；公开表还会暴露整张表。
IM

IM 非 owner

被当成 owner

外部 IM 发送者按 agent owner 执行；只有 owner 自己的绑定被信任；群聊 / 话题私聊 subject 不是人。

群成员可能借 Agent 以 owner 身份操作应用；个人链接只能发给 owner。
单

一次性提交者

只读

扫码填表、活动报名、公开收集。公开面没有行写入 / 提交能力；为每个填表人建持久 guest 又太重。

需要「提交令牌」而不是「账号」，否则产生大量休眠主体和 PII。
匿

匿名访客

只读

公开链接访问者，token 即凭证；不能写、不能 generate、不能 launchGame。

公开面只放「即使泄露也可接受」的数据；个人数据不进公开表。

结论：外部参与者需要「应用成员 + 表级可见性 + 只作用于该应用的会话」；一次性提交者需要「短期提交令牌」。 把所有人塞进一个 users.kind=guest，只是把复杂度藏起来。

方案取舍 · OPTIONS

A / B / C'：为什么是「统一主体 + 双模式参与者」

C' 不是把所有人变成 guest，而是把「持久参与者」和「一次性提交」分开。
维度A · 全部开 Octop 账号B · 独立 App 账号体系C' · 统一主体 + 双模式 推荐
外部参与者高：邀请 / 审批 / 账号低：应用自己发账号低：加入码 / IM 绑定 / 提交令牌
一次性表单重：每个填表人开账号可做，但仍是账号轻：submission token，不建持久主体
复用现有 user_id FK100%低：ACL / 行 / 历史 / 申请全部多态化高：PrincipalDirectory 隔离底层，业务按接口用
账号表污染高无低：users.kind 第一版 + 凭证 scope 隔离；长期可迁独立表
与 IM 绑定先开账号再绑定需要双映射直接绑定到 member / guest；submission 不绑定
主要代价账号膨胀、外部联系人混入第二套身份 / ACL / 审计要先做 PrincipalDirectory + 授权矩阵 + 表级可见性

边界：C' 不是多租户隔离（docs/miniapp-overview.md:63）。guest 只是同一实例内的持久参与者； 一次性提交者用签名令牌，不进入 users。如果目标是 SaaS 多租户，应直接规划 B 或独立 principal 表。

行作用域

非 owner 在 row_scope=user 表上只看/写自己；row_scope=app 表上按角色看全部。edit_data 不是「user 表全表编辑」。

表级可见性

light_app_tables.member_visible 默认 0；owner 显式开启 participant 可看的表。public_visible 只影响公开链接。

PII 行级

view 始终脱敏；participate 自己的行不脱敏、他人行脱敏。响应加 masked_pii_rows / masked_pii_columns。

授权矩阵：每个端点都要声明 action（view_row / write_own / write_any / export / aggregate / structure / share / ai / service）， 再由 authorize() 结合表可见性、row_owner、PII 判定；不能只查 app 级 permission。

MiniApp 用户管理 · MEMBERS

管理面在 Dashboard：成员 + 表级可见性 + host policy

应用 owner 管成员；agent owner 管是否允许外部共享；平台管理员只管平台账号与滥用处置。

员成员与访问

  • 成员列表：平台成员 / guest / 待审批；角色、来源、最后活跃、创建行数
  • 邀请：用户名 / 加入链接 / 二维码 / 个人一次性链接；可设角色、TTL、次数、审批
  • 表级可见性：逐表勾选 member_visible；默认关闭，form 表显式开启
  • 批量：CSV 导入、搜索、分页、导出成员、批量移除
  • guest 门户：/my 列出已加入应用、重新进入、退出/删除

单一次性提交

公开表单用 submission token：绑定 app + table + TTL + 次数，不建 guest。P3 提供；P1 先做邀请制 guest。

策应用级策略

  • access_policy：private / invite / public_read（org 留给 P3 用户组）
  • 默认角色、成员上限、加入码 TTL / 次数、是否需要审批；外部邀请走 app_member_invites
  • guest 默认关闭 ai；P1 固定拒绝，不承诺 per-action 配额
  • participant 固定不能 export / aggregate 全表（P3 再评估按成员开启）

治Host policy

  • agent 级 external_sharing_policy：是否允许外部参与者、guest 上限、是否需 host 审批
  • app owner = agent owner 时可直接邀请；不同 owner 时默认需 host 审批
  • 成员页展示 host 策略；被拒绝时给出原因，不让 owner 误以为系统坏了

审审计与同意

member.join / role / remove、join_code、identity.bind、host.approve 全写审计；加入页展示数据处理说明与同意勾选。

四条路径，两个解耦，一个 host 闸门

应用访问不需要 Agent 访问；但跨 owner 邀请外部参与者需要 host 同意。

1解耦：应用 ≠ Agent

app-scoped JWT 只允许 /api/apps/{app_id} 子树和少量只读启动接口；/api/agents 直接 403。外部参与者不需要被共享 Agent。

2解耦：共享 Agent ≠ 共享应用

agents.is_shared 只影响聊天；应用访问仍走成员关系 + 表可见性。agent owner 的 host 只读权限保留，但不自动推导给所有人。

闸Host 闸门

app owner ≠ agent owner 时，默认需要 agent owner 批准外部共享；agent owner 可设 guest 上限 / 关闭外部参与。避免别人用你的 workspace 和模型额度招待外部用户。

IM 入口 · 链接 / 会话 / 分层
IM 接入 · BOUNDARY

群聊只做公开信息；个人数据回私聊 / WebView

这是 v3 收紧的地方：群聊不发加入链接，也不执行个人应用工具。

群群聊六条规则

  • 只发公开链接；不发个人入口码，也不发多用途加入链接
  • 所有 app 数据工具要求 owner_verified；未绑定 / 群聊只能拿链接
  • 不回答个人数据查询；个人数据只在私聊或 WebView 返回
  • sender_id 只用于归属与展示，不作为可信身份
  • 个人操作要求 已绑定 + 私聊 + 应用成员
  • 需要个人信息时，引导用户私聊或打开应用链接

八条必须始终成立

2
Principal 隔离

3
会话作用域

4
表 / 行双重判定
participant 只能读 member_visible 表；user 表只看自己的行；row_owner ≠ created_by。
5

6
加入码 / 邀请原子性

7
渠道绑定不可抢
同一 (channel, account_key, sender_id) 已绑定其他用户时拒绝覆盖；legacy '' 只做回退；写审计。
8
IM 边界
群聊只发公开链接；P2a 所有 app 数据工具要求 owner_verified；guest 绑定走 /link；P2b 先隔离 thread / memory。

验收 · P0 / P1
决策 · DECISIONS

八个关键决策，建议默认值

先定 guest 角色 / 凭证 / 邀请模型，再排 P0；这四条决定后面所有实现的形状。
1
身份模型选 A / B / C'？

C' 统一 PrincipalDirectory + 双模式参与者；users.kind 是第一版实现，不是临时补丁。

建议 C'
2
guest 能持什么角色？

view 能读全部表并导出，会绕过表可见性；guest 只能 participate，view 留给平台成员。

建议 guest 仅 participate
3
guest 凭证用 cookie 还是 token？

app iframe 是 opaque origin，不带 cookie；app-scope 白名单又排除了 Path 作用域。

建议 guest scope + app token，P1 无 cookie
4
外部邀请放哪张表？

外部人在邀请时没有 users 行，app_access_requests.requester_user_id 放不下。

建议 app_member_invites
5
PII 怎么脱敏？

行级：view 始终脱敏；participate 自己的行不脱敏；响应带掩码标记。

建议行级 can_view_pii
6
IM actor 先做还是后做？

P2a 只做链接 + 数据工具 owner-only；P2b 的 actor 以 thread / memory 隔离为前提。

建议 P2a 先行
7
跨 owner 外部邀请默认值？

默认关闭外部参与；guest 与不在 agent 范围内的 member 需要 host 审批。

建议默认 host 审批
8
per-action 配额现在做吗？

现有只有 token lifetime quota；export / aggregate / service 对 participate 直接拒绝，不需要新配额。

建议 P1 不做，单独立项

下一步：P0 先落地 PrincipalDirectory + 三种凭证 scope + authorize() + rank 清零 + PII / /shares； schema 提前到 P0；不动 UI、不建 guest。P1 再开成员 / 邀请 / 加入码 / 会话。
