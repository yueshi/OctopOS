零售经营场景 × Octop 差距分析

2026-11-16 来源：智总管产品功能分层调研汇报 v3（四层十一模块，54 页） 口径：Octop 现状以代码为准 方法：6 路并行代码调研 + 关键论断逐条抽验 同源：docs/retail-scenario-gap-analysis.md
结论：Octop 是通用 Agent 平台底座，不是零售经营系统。它天然吃下 PDF 十模块里的 连接层（0.1 部分 / 0.3 完全）与输出形态（3A、3B 的"形"）； 感知层（1.2）零件齐、缺最后一段装配；洞察层（2A、2B）与数据层（1.1、1.3）基本是空的 —— 这四块要建的是一层「门店 / 零售业务契约」（标准业务表 + 指标层 + 客户档案 + 归因口径）， 不是平台能力。

文档里"没做过一次"的那几件（客户画像、经营归因、实时参谋、平台数据监测），在 Octop 里同样一次都没做过。

1 · 场景清单与平台需求提炼

0 连接0.1 IM 全通多平台对话统一接入，AI 能读到、能回复、断点提醒人接手必做 = 企微 + 公众号 + 飞书 + 钉钉；灰度 = 抖音 / 小红书私信；不做 = 微信个人号
0.2 平台监测盯客户自己的小红书 / 抖音 / 视频号 / 公众号号：粉丝、曝光、评论、私信自建 = 公众号 + 抖音自有号授权；不做小红书；不做代运营
0.3 外部搜索查公开信息（政策、同行、价格），能给出处必做 = 博查 + 智谱两家；不接阿里云；搜不到要说"没找到"

3 输出3A 销售支持店员当场能查能说出口；答案必须出现在同一个 IM 窗口知识来自门店自己的产品库，不做独立 App
3B 经营驾驶舱老板每天早上打开的一个页面：结论—数字—异常—待办不做报表；每条建议带"一键改 / 生成 / 打电话"按钮；底部写数据来源
3C 营销短视频自有素材 + 行业模板 → 出片、批量分发、回答"带来几个到店客人"只做"素材 + 模板 + 到店归因"；不做一键成片、不做换脸

3 · 逐模块详评

0.1 IM 全通 部分满足

Octop 现状

  • ✓ 10 个内置通道，全部能读能写：企微 aibot WebSocket（octop_gateway/channels/wecom.py:67）、飞书 WS 收 + REST 发（支持 post / interactive）、钉钉 Stream 收 + OpenAPI 发、微信 iLink Bot 长轮询、QQ / Telegram / Discord / 元宝 / 小艺 / MQTT。
  • ✓ 群聊语义完整：GroupVisibility / GroupActivation / GroupHistoryMode（octop_gateway/group_context.py:21-56）。
  • ✓ 会话持久化：sessions（含 channel_type / channel_subject_id）+ threads + thread_messages（infra/db/repos/sessions.py:59-72）；thread key 含 channel_type（infra/gateway/threads.py:36-45）。
  • ✓ 主动推送四条链路：cron（infra/cron/delivery.py:130）、external events outbox（infra/events/expert_target.py:102）、主动关怀（infra/proactive/service.py:252）、团队通知（infra/agents/teams/team_manager.py:1474）→ 统一出口 infra/gateway/gateway.py:824。
  • ✓ HITL 成熟：hitl_pending 表，状态 pending/approved/rejected/expired（infra/gateway/hitl/store.py:16-24），kind = approval / ask，TTL 30 分钟，IM 内用 /approve /reject /pending 斜杠命令（infra/gateway/slash/catalog.py:18）；cron 遇 HITL 会挂起而非失败（infra/cron/delivery.py:243-270）。
  • ✓ 富文本能力矩阵（docs/miniapp-im-optimization.md:113-121）：飞书 interactive card / 企微 Markdown / 微信纯文本+图 / QQ 纯文本。

不足

  1. 微信公众号没有通道。catalog 30 个连接器与 gateway 通道里都没有公众号回调端点，api/routers/ 下无 IM callback 入口。PDF 把公众号列为四个合规平台之一 —— 这是 0.1 的唯一硬缺口。
  2. 没有外部联系人 / 身份归并。IM 消息一律映射到 agent 属主，源码注释写明 "IM members of one agent share the owner's profile, they are not isolated from each other"（infra/gateway/process/message_keys.py:86-108）。企微里的张三和抖音里的张三是两个 session、两个 thread、同一个 users.id。PDF 0.1 的核心命题「十年后还在用同一个入口」在 Octop 里没有对应物。
  3. 没有"转人工接管"。handoff 只存在于浏览器控制权（api/routers/browser/harness.py:298），与 IM 无关；没有「AI 挂起 → 通知人工 → 人工接管回复」的状态机。
  4. 无平台历史消息回溯：octop_gateway/channels/ 全目录无 fetch_history。
  5. 主动推送有前置条件：必须先有 session（对方发过消息），否则推不到。
  6. 企微缺「客户联系」与「企微客服」两个子通道（docs/architecture-overview.md:401-402）。

0.2 平台监测 未覆盖

Octop 现状

30 个内置连接器（infra/connectors/catalog.json）里没有抖音、公众号、视频号、小红书的数据连接器；infra/events/connector_poll.py 只能轮询已有连接器。理论上可用 octop-browser（CDP 驱动 Chrome）打开自有号后台做 RPA 抓取 —— 但这正是 PDF 2.2 判定的"高风险、要做爬虫法律风险"路径。

建议不做成平台模块。PDF 自己也把它定成"客户级数据定制（公众号号自研 + 抖音采购 + 小红书不硬碰），自研投入控制在 2 个月内"。落到 Octop 上，正确形态是：
① 为单个客户写死一个采集 MCP（账号授权 + 轮询），进 connectors 目录当客户实例；
② 数据落到该客户专属的 light_app 表（light_app_sources + light_app_rows）；
③ 在 dashboard 里用 MiniApp 看板呈现"评论里问价格的人 → 销售线索"。
即：0.2 降级为 3B 的一个数据源，而不是一个平台子系统。

0.3 外部搜索 已满足

Octop 现状（代码为准，文档里查不到）

  • ✓ harness 内建 web_search 工具族：tavily.py / kimi.py / _registry.py（octop_harness/builtin/tools/web_search/），注册为 5 个工具（infra/agents/settings/tool_catalog.py:72-76：tavily / brave / google / kimi / searchfree）。
  • ✓ web_fetch 工具：抓 URL 转 markdown，带 SSRF 防护与 5MiB 上限（octop_harness/builtin/tools/web_fetch.py:1-30）。
  • ✓ 设置页可探活：POST /api/search/{provider_id}/test（api/routers/search.py:26），provider 集合 tavily/brave/google/kimi（infra/utils/search_probe.py:20）。

不足与补法

几乎无。只需两件小事：

  1. 提示纪律「搜不到就说没找到，严禁自行补全」+ 每条结论附来源站点 —— 写进 Agent 系统提示 / SKILL.md；
  2. 少量「时效性 / 长尾事实」确实答不上时，属模型能力边界，不是平台缺口。

结论：配两个 provider（对应 PDF 的"博查 + 智谱"）即可开工。

1.1 ERP 只读适配器 未覆盖

Octop 现状

  • ✕ 零业务表。53 个 repo（infra/db/repos/）全是平台表：agents / channels / threads / cron / connectors / knowledge / light_app_* / teams / goals / external_* / trajectory …没有订单、库存、客户、商品任何一张表（已用 CREATE TABLE 全量扫描确认）。
  • ✕ 无数据库类连接器：30 个 catalog 条目里无 MySQL / PostgreSQL / SQL Server，也无 Airtable / Sheets / CRM。venv 里只有 psycopg，没有 pyodbc / pymssql / mysql。
  • ✓ 凭据加密有：infra/connectors/crypto.py:14（Fernet，密钥进 secrets 表）。
  • ✓ 自定义 MCP 有：infra/connectors/custom_mcp.py:17，支持 streamable_http 与 stdio。
  • ✓ 中间层载体已现成：light_app_sources 表带 mode(append|snapshot)、schedule_seconds、mapping_json、upsert_key（infra/db/migrations/025_light_apps.sql:68-79），行落 light_app_rows —— 这正是"定时拉取 + 字段映射 + 幂等去重 + 落表"四件套。
  • △ 但数据源只吃进程内 gateway 连接器：infra/apps/sources.py:1-7 明写 "Only in-process gateway connectors (mcp_mode=gateway) are supported … HTTP MCP servers would need a client stack in Octop — out of scope for now." → 自定义远程 MCP 不能当 light_app 数据源。
  • △ http-extract 只支持公共只读、无鉴权的 GET（infra/connectors/gateway/adapters/http_extract.py:21-47）。
  • ✓ 只读强制有一处：infra/apps/sources.py:91 _require_read_only 按 MCP readOnlyHint 拒绝写工具。
  • ✕ 无增量水位（CDC）、无表结构识别、无字段语义映射、无清洗规则。

如何补（最小可行路径）

  1. 新增 SQL Server gateway adapter（进程内 Python adapter，走 pymssql），进 catalog.json 并标 readOnlyHint=true → 立刻能被 light_app_sources 当数据源（这一步解开 sources.py:1-7 的限制）。
  2. 每家客户做一份 mapping（表名 → 列名 → 语义），AI 生成初稿 + 人工确认，存进 light_app_sources.mapping_json。
  3. 四张标准表建成 4 个 light_app 表（订单 / 库存 / 客户 / 商品），mode=append + upsert_key 幂等，schedule_seconds 设为夜间频率。
  4. 只读双保险：数据库侧只读账号 + DENY INSERT/UPDATE/DELETE（PDF 2.4.2 的 SOP）；应用侧 _require_read_only 兜底。
  5. 兜底路径（客户只有 Excel）：走 workspace 落盘 + miniapp 导入 / light_app_sources 的 workspace_file 源（infra/apps/service.py:405-407）。
  6. CDC / 增量同步先不做：upsert_key + 定时全量 append 已能覆盖 PDF 说的"每晚更新一次"。
PDF 判定这个模块"前两段是人工（表结构识别 ~40%、字段语义映射 ~30%），不是技术密集型，是耐心密集型"。 Octop 的技术缺口其实只有一个小点（SQL Server 适配器），真正的活是每家客户的映射。

1.2 屏幕与会议实时读取 部分满足

Octop 现状

  • ✓ 截图能真正进模型：browser_use 截图返回 [image_block, text_block] 多模态块（octop_harness/builtin/tools/browser_use.py:126-174，media_type: image/png），注册于 agent.py:1367 / tool_catalog.py:66。
  • ✓ 桌面截图工具：desktop_screenshot 抓 X11（mss / ImageMagick），PNG 落在 agent workspace outbound/screenshots/（octop_harness/builtin/tools/desktop_screenshot.py:288-345）。
  • ✓ 实时 ASR：腾讯云实时 STT（infra/voice/realtime.py），WS /api/voice/stt-stream（api/routers/voice.py:256）；浏览器麦克风采集（dashboard/src/hooks/useVoiceInput.ts:323 getUserMedia / :479 MediaRecorder）。
  • ✓ 推流：浏览器 4fps JPEG WS（api/routers/browser/stream.py:335）、远桌面 WS（JPEG + 键鼠注入，api/routers/desktop/stream.py:235）。
  • ✓ OCR 引擎可用：rapidocr 额外依赖（pyproject.toml:75-78）；ocr-and-documents 技能提供 PDF / 扫描件抽取（pymupdf / marker-pdf）。
  • ✓ 腾讯会议官方 MCP（infra/connectors/catalog.json:60-79，mcp.meeting.tencent.com/mcp/wemeet-open/v1，infra/connectors/builder.py:179）。
  • ✓ 可注入进行中的一轮：steer 支持 image / file 块（infra/gateway/steer/coordinator.py:666-687），且块格式是 workspace_path 引用 —— 与 desktop_screenshot 的落盘路径正好对上。
  • ✕ 截的是服务器虚拟桌面 / 受控浏览器，不是用户本机屏幕；无本机上行通道。
  • ✕ 无"持续感知 → 自动触发推理"的回路。事件平面是摄入侧（webhook / 300s 轮询，infra/events/worker.py:677-681），截屏流只到 dashboard，不回流 Agent。
  • ✕ 无无障碍树（只有 CDP DOM.getDocument 的 DOM 文本 → canvas 应用读不到字），需 OCR 补。
  • ✕ 飞书会议 / Zoom 无接入；腾讯会议以会后录制 / 纪要为主，非逐句实时。
  • ✕ 无桌面悬浮窗 UI；桌面壳无麦克风采集。

如何补

  1. 原型（最短路径，零件全在）：桌面壳加「截屏 + 麦克风上行」→ 帧写入 agent workspace outbound/screenshots/ → steer 以 image 块注入进行中的一轮 → 模型结合 ERP 历史（1.1）与转写文本给建议。缺的只有"帧怎么上来"和"什么时候注入"。
  2. 产品化：加一个采样循环（屏幕帧 + 转写片段），做节流与去重；注入策略改为新轮次（而不是 steer 打断），并保留 steer 作为"老板插话"通道；canvas 场景补 rapidocr 识别；单进程 ws_hub 补跨机扇出（目前无 Redis pub/sub）。
PDF 的关键判断是"先读录音转文字，再实时截屏；当'做'优先 —— 先看画面，树里没有目标文本不裁剪"。 Octop 的默认做法是反的：截图是工具调用触发的（人点一下），不是持续采样。

1.3 客户分层与档案 未覆盖

Octop 现状

  • ✕ 无客户表、无标签表、无分层模型（全仓无 customer / contact / lead / segment / RFM 业务表）。
  • ✕ knowledge_bases / knowledge_documents 是文档型 RAG：每 KB 一个 SQLite sidecar 存向量，查询全表余弦扫描，无全文 / BM25、无字段过滤（infra/knowledge/index.py:25-35）；k=8、上下文预算 6000 字（infra/knowledge/retrieve.py:17-24）。不能当客户档案用。
  • △ CSV / XLSX 进知识库会被拍平成 tab 分隔文本再切块（infra/knowledge/parse.py:45,74,262）→ 列语义丢失、不能按价格 / 库存过滤、无实时性。商品表绝不能这么进。
  • △ IM 身份塌缩到属主（infra/gateway/process/message_keys.py:86-108）→ "沟通记录"无法按客户归集，这是 1.3 的硬阻碍。
  • ✓ 载体可用：light_app 自定义表 + 行 + PII 机制（infra/apps/pii.py）。

如何补

  1. 依赖 0.1 的 contacts 层（外部联系人 + 身份归并）—— 否则沟通记录无法归集客户。依赖关系明确，先做 0.1。
  2. 客户档案落 light_app 表：customers（客户 id、累计成交价、到店次数、最近到店时间、首单时间）+ orders 明细表。
  3. 累计成交价不要预计算成字段：每次现算（订单表按客户聚合），避免"同一客户多套价格"的历史漂移 —— 这正是 PDF 点名的坑。
  4. 分层不要做规则引擎：PDF 说"不用老模板，系统自己算"。让 Agent 在夜间跑批里读表 + 算铁杆 / 潜力 / 沉睡 / 走 + 写回 tag 列（app_update_row 已有）。符合"最小实现"原则。
  5. 沟通记录侧：contacts ↔ sessions 关联，让 Agent 能读"这个客户上次说什么"。

2A 经营诊断与归因 部分满足

Octop 现状

  • ✓ 夜间跑批机制齐全：cron 触发四类 —— cron: / interval: / date: / agently:（infra/cron/trigger.py:77）；task_type = text（直推）/ agent（跑完整 ReAct 回合，infra/cron/task_type.py）；cron job 可挂 MCP servers（infra/db/repos/cron.py:92）。
  • ✓ 结果推 IM：infra/cron/delivery.py:71 → gateway.push_session_text → 通道发送。
  • ✓ 数字可信机制：Light App 服务端聚合 + 声明式图表 spec（infra/apps/charts.py:20，6 种图表 + sum/avg/count/min/max），只读助手防模型编数（infra/apps/assistant.py）。
  • ✓ 决策链可回溯：trajectory_events append-only 事件流（infra/history/trajectory/，REST api/routers/chat/trajectory.py:239-380）。
  • ✕ 无指标层：毛利、进货价、周转天数这些口径没有定义处。
  • ✕ 无归因算法：价 vs 量 的分解只能靠 LLM 即席生成，无确定性算法层。
  • ✕ 无诊断产物表：cron 只留 last_run_at/last_status/last_error（infra/db/repos/cron.py:94-96），产物落在 thread_messages 里 → "昨晚 03:12 产出的那份诊断"无处可查。
  • ✕ 无异常阈值与告警规则；无 pandas / matplotlib（venv 只有 numpy）→ 计算需在 execute 沙箱自行装依赖。
  • ✕ 跨天跨源归因无关联边（trajectory 是单会话流）。

如何补

  1. 指标层：把毛利 / 进货价 / 周转定义成显式配置（指标名 + 计算式/映射 + 口径说明 + 适用门店），存 light_app 表或 settings，不要硬编码进 prompt。这是 2A 与 3B 的共同前置。
  2. 诊断产物表：新建 diagnostics（run_at, agent_id, job_id, scope, metric, conclusion, evidence_json, confidence, source_note）。同时解决 2A"无处可查"与 3B"底注要写昨晚 03:12 同步"。
  3. 归因：不必写算法库 —— 让 Agent 在跑批里做价/量分解并把证据链写进 evidence_json；若要确定性，用 light_app 的服务端聚合做对照，LLM 只负责叙述。
  4. 异常检测：先做「环比波动超阈值 → 标注」，阈值入配置。
  5. 依赖：指标层依赖 1.1 的四表落地，否则毛利算不出来。

2B 实时参谋 部分满足

Octop 现状

  • ✓ chat WS 逐 token 推送 + turn 内 steer（api/routers/chat/ws.py:280-292）；steer 支持 image / file 块（infra/gateway/steer/coordinator.py:666-687）。
  • ✓ HITL 审批、WS hub 扇出（infra/gateway/ws/ws_hub.py:129）。
  • ✓ 实时 ASR（腾讯）+ 截图可进模型（见 1.2）。
  • ✕ 无秒级自主建议回路：没有任何组件持续监听屏幕 / 音频并自动触发一轮推理；事件平面是摄入侧 + 300s 轮询（infra/events/worker.py:677-681）。
  • ✕ steer 的块是 workspace_path 引用而非原始图片 → 帧必须先落 workspace（可行，见 1.2）。
  • ✕ 单进程 ws_hub，无跨机 pub/sub。
  • ✕ 无客户历史成交价 / 账期数据源（依赖 1.1、1.3）—— PDF 明确说这是 2B 的前提。
  • ✕ 无本地指标缓存 → 每次对标都要查 ERP，达不到 ≤2–3 秒。

如何补（按 PDF 建议的优先级）

  1. 先做「会前准备」（低延迟、价值立刻可见）：cron date: 一次性触发 → 生成一页纸（历史成交价 / 账期 / 最近投诉 / 预判异议）→ 推 IM 或落 workspace。这条链路 Octop 现有能力全部具备，缺的只是客户档案数据（1.1 / 1.3）与模板。
  2. 再做「会中提示」（高难度，需三件同时到位）：① 屏幕帧 + 转写片段的持续采集（1.2）；② 指标 / 历史数据的本地毫秒级缓存（不能每轮查 ERP）；③ 一个低延迟触发器，把新观测作为新轮次输入，同时保留 steer 插话通道。
  3. 延迟预算：PDF 说 1–2 秒对结论完全够用，不需要客服级的 500ms —— 这意味着不必追求流式，一个 1–2 秒一帧的采样 + 小模型判据就够，别过度设计。
PDF 的判词很准："国内把'实时'做成了'实时看板 / 实时预警'，那是给老板看的监控，不是给销售用的提示"。 Octop 目前连看板那种都没有，更没有提示 —— 但它有 PDF 没提到的优势：steer 机制天然支持"在对话进行中把新观测喂进去"。

3A 销售支持 部分满足

Octop 现状

如何补

  1. 商品 / 价格 / 库存 → 进 light_app 表，不进知识库；异议话术、常见案例 → 进知识库（文档形态正确）。检索时 Agent 先查结构化表（app_read_data）再查话术库。
  2. IM 交付：企微 / 微信用「Markdown + 一张商品图 + 链接」——现有能力够用；要真卡片与按钮，需飞书或另做企微侧。
  3. 新人识别：依赖 0.1 的 contacts 层（按 sender 计数 / 首触标记），不要指望 users 表。
  4. 店长维护：需要补 KB 按角色 / 门店的 ACL（当前只有 owner / shared 二选一），否则"店长维护话术"没有权限落点。
  5. 四类异议话术（太贵 / 想再看看 / 别家更便宜 / 效果不好）做成 4 个 SKILL.md 或一个带分类的文档集，人工维护 —— 与 PDF 的"话术库由谁维护"结论一致。

  5. 推送：先用 IM 纯文本简报（cron 已能推，infra/cron/delivery.py:130），app 级 SSE 后置。

5 · 建议路线（按依赖顺序，不按热闹程度）

阶段 0 · 地基（无依赖，先做，1–2 周）

  1. contacts 外部联系人表 + 跨平台身份归并（解 0.1 / 1.3 / 3A）
  2. diagnostics 诊断产物表（解 2A / 3B 的共同前置）
  3. SQL Server 只读 gateway adapter（1.1 唯一的技术缺口；注意 infra/apps/sources.py:1-7 限定数据源只吃进程内 gateway 连接器，远程 MCP 会被拒）

阶段 1 · 数据层（依赖阶段 0，2–4 周）

  1. 四张标准表落 light_app（订单 / 库存 / 客户 / 商品）；一家客户跑通 = 一套模板
  2. 指标层定义（毛利 / 进货价 / 周转）+ 归因提示规范
  3. 客户档案 + Agent 现算分层（不写规则引擎）

阶段 2 · 输出层（依赖阶段 1，2 周）

  1. 简报页 + 四段式模板 + 来源脚注 + 3 个埋点事件（open / click / adopt）
  2. 待办结构化动作（改价 / 生成话术 / 打电话）
  3. KB 按角色 / 门店 ACL（店长维护话术的权限落点）

阶段 3 · 实时层（依赖阶段 1，风险最高，3–4 周）

  1. 桌面壳屏幕 + 麦克风上行 → steer / 新轮次注入 → 会中建议
  2. 指标本地毫秒级缓存（对标不能每轮查 ERP）

建议明确放弃 / 降级的

  • 0.2 平台监测 → 降级为客户级数据定制（不进平台）
  • 3C 的一键成片、换脸、批量分发 → PDF 已判定不做，Octop 同
  • 2B 的"会中提示"若排期紧 → 退回"会前准备"（cron date: 一行就能起）
  • 多租户化 → 沿用现行"每客户 / 每门店一个实例"（docs/agent-os-roadmap.md:32），不要为这十个模块引入 tenant 维度
