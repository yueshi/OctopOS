1. 结论摘要

这套方案的核心不是“再做一个知识库”，而是把三件原本分散的事接成一条闭环：

Ontology（契约）：定义对象、关系、动作、约束与版本。
↓
知识图谱（事实与证据）：存节点、边、别名、来源、置信度。
↓
LLM（理解与生成）：抽取、查询理解、答案生成、实体消歧、动作提议。
↓
主动式 Agent（发现与行动）：触发器、策略、上下文、规划、执行、交付、反馈。
↓
治理（HITL / 预算 / 审计 / 评测）：保证不越权、不失控、不骚扰。

四条核心判断

  1. 图 / 本体是基座，LLM 是入口和出口，Agent 是行动者。不要让 LLM 当数据库、权限或真相源。
  2. 结构化数据确定性建图，非结构化数据 LLM 抽取。MiniApp 的 reference 列已经是边，不需要 LLM 再抽；文档 / 对话才需要。
  3. 主动性分级：观察 → 建议 → 审批执行 → 低风险自动 → 自治。第一版只做 L0/L1，不要一上来做自治。
  4. 产品化 = 内核 + 上层本体 + 行业 Pack + 项目映射。不要做万能本体，也不要先做市场。

为什么这样分层：

  • LLM 不在最底层，也不在最高层。它属于智能层，向上服务消费层，向下受图谱层和治理层约束。
  • 图谱层不直接依赖 LLM。确定性映射、查询执行、权限判定都不经过模型，保证可复现、可审计。
  • 治理层是横切的。任何一层产生写操作、外发消息、成本消耗，都要经过 ACL、HITL、预算与审计。
  • 数据层不重建。复用现有 MiniApp、知识库、memory、连接器，不另造一套存储。
边界提醒：Octop 当前是单实例产品（docs/miniapp-overview.md:69），不是多租户隔离载体。本文所有“多项目复用”默认指同一实例内多 Agent / 多 MiniApp / 多知识库，或“每客户一套部署”；多租户 SaaS 需要单独的架构改造。

3. 三条技术线

3.1 Ontology：可执行的类型契约

本体不是 ER 图，也不是 OWL 文件。它必须被写入校验、查询、Agent 工具、页面和动作消费，否则一定腐化。

层 内容 不做的后果
类型层 对象类型、关系类型、动作类型 图只是一堆没有语义的节点 / 边
约束层 属性类型、必填、枚举、基数、from/to、唯一键 脏数据直接进图，查询不可信
映射层 源表 / 文档 / 记忆实体 → 节点 / 边 图和业务数据脱节，很快过期
消费层 写入校验、查询、Agent、UI、动作、权限 本体只存在于文档里，没人使用

3.2 知识图谱：事实、关系与证据

数据模型

表 职责 关键字段
graph_ontologies 本体注册与版本 graph_id, schema_json, version, status, owner_user_id
graph_nodes 节点实例 node_id, node_type, canonical_name, properties_json, confidence
graph_edges 边实例 edge_id, edge_type, src_node_id, dst_node_id, valid_from/to
graph_aliases 实体别名 node_id, alias, normalized_alias, source
graph_sources 来源与同步状态 kind, ref, source_hash, last_synced_at, status

两条建图路线

路线 A：结构化数据（确定性）

light_app_rows + reference 列 → 节点 / 边。LLM 不参与建图，只参与查询理解、答案解释、动作提议。

优点：零抽取误差、可复现、成本低。

落点：src/octop/infra/apps/models.py:291 的引用列校验。

路线 B：非结构化数据（LLM）

文档 / 对话 → LLM 抽取候选节点 / 边 → 本体校验 → 实体消歧 → 入图。

护栏：类型必须在 ontology 内；每条边必须有 evidence；低置信度进人工复核。

落点：src/octop/infra/knowledge/jobs.py:35 的索引任务旁新增抽取 job。

Provenance：每条边都要能回答“你凭什么”

{
  "source_kind": "kb_chunk",
  "source_ref": "kb_01:doc_18:3",
  "confidence": 0.92,
  "status": "active",
  "valid_from": "2026-01-01",
  "valid_to": null
}

查询能力

  • neighbors：1–3 跳邻域，支持边类型 / 方向过滤，递归 CTE + 深度上限。
  • path：两个节点之间的路径，双向 BFS，最多 4 跳。
  • search：按类型、名称、别名搜索；SQLite FTS5 / PG 前缀索引可选。
  • subgraph：给 UI 的紧凑子图，节点 / 边数量有上限。

3.3 主动式 Agent：发现、建议、执行、验收

触发器：cron / 外部事件 / 数据变化 / Webhook / 连接器轮询 / 图变化
↓
策略过滤：免打扰、频率、预算、去重、优先级
↓
LLM 分诊：值得行动吗？多紧急？影响谁？
↓
上下文构建：子图 + MiniApp 行 + 知识库 chunk + memory
↓
LLM 规划：步骤、工具、预期结果
↓
执行：只读 / HITL 审批 / 低风险写
↓
交付：通知中心 / IM / MiniApp 卡片 / 看板
↓
反馈与验收：接受 / 拒绝、动作结果、记忆

主动性分级

级别 行为 例子 门槛
L0 观察 只记录 / 告警，不改数据 退款异常日报 证据、去重、免打扰
L1 建议 给出建议动作，不执行 “建议暂停 V001” 建议准确率、可解释
L2 审批执行 准备好动作，等人批准 “一键批准退款” HITL、幂等、审计
L3 低风险自动 可逆、低风险动作自动执行 补别名、重建图、发提醒 预算、回滚、kill switch
L4 自治 多步任务自主闭环 自动处理售后工单 预算、Verifier、异常收件箱、SLA
建议：第一个版本只做 L0/L1；跑 2–4 周，测告警准确率和接受率，再进 L2。L3/L4 需要先补预算闸门、无人值守 HITL、独立验收（docs/team-l3-roadmap.md 的 A1/A2/A3）。

4. LLM 的直接参与

“直接参与”的定义：LLM 实际被调用，并且它的输出直接进入下一步。按这个标准，LLM 直接参与 6 个环节，其中 3 个必需、3 个增强。

环节 LLM 做什么 是否必需 护栏
文档实体 / 关系抽取 从 chunk 输出受本体约束的 JSON + 证据 必需 类型校验、证据必填、低置信复核
查询理解 自然语言 → Query DSL（实体 / 路径 / 过滤 / 聚合） 必需 后端校验类型 / 边；不生成裸 SQL
答案生成 读子图 + 证据，生成带引用回答 必需 只引用返回证据；证据不足说“不知道”
实体消歧 判断别名 / 重名是否同一实体，给置信度 增强 阈值 + 人工复核，不自动静默合并
Agent 规划 选择 graph / knowledge / app 工具，多步执行 增强 工具 schema + 轮次 / 预算上限
动作提议 提议动作、参数、前置条件 增强 本体 action + HITL + 审计

LLM 不直接参与的环节

环节 谁做 为什么不用 LLM
MiniApp 行 → 图 确定性映射 reference 列已经是结构化边
图查询执行 SQL / CTE / 双向 BFS 需要可复现、可审计、可优化
计数 / 求和 / 排序 数据库 LLM 算术不可靠
权限判定 / PII 脱敏 ACL / 规则 安全不能靠概率
事务 / 审计 DB + audit_log 必须原子、可追溯
图渲染 Cytoscape / G6 前端确定性渲染
一句话：LLM 直接参与“从文本到图”和“从问题到答案”的两端；中间的事实层是确定性的。它的输出永远是“提议”，由校验器、查询编译器、ACL 和 HITL 决定是否采纳。

5. 落地原则

1本体先行，但只做最小可用本体

5–8 个对象、5–8 个关系、1–2 个动作，围绕 20 条能力问题。只在一个场景出现的概念，不进 core.*。

2图是派生 / 证据层，不是第二真相

每条边带 source_kind / source_ref / confidence；派生边可按 source_hash 重建，手工边单独标记。

3结构化数据确定性建图

MiniApp reference → 边；LLM 只在查询 / 回答 / 动作层。不让 LLM 对结构化数据再抽一遍。

4非结构化数据 LLM 抽取

文档 / 对话 → 候选节点 / 边 → 本体校验 → 消歧 → 入图；没有证据的抽取直接拒绝。

5LLM 只做理解 / 生成 / 提议

不做 ID、权限、聚合、裸 SQL、自动合并。事实、权限、聚合、审计由确定性系统负责。

6主动性分级

先只读观察，再建议，再审批执行；L3/L4 需要预算、HITL、Verifier、kill switch。

7先关系库，后图数据库；先 Pack，后市场；先单 Agent，后多 Agent

不要第一版就引入 Neo4j / 多 Agent / 市场。先用现有 SQLite/PostgreSQL 跑通闭环，再按规模与需求演进。

6. 90 天路线图

M0 · 契约与准备

第 1–2 周

目标：把“以后改起来很贵”的契约定下来。

  • docs/ontology-kernel-adr.md：属性图 vs RDF、存储、Pack 边界、版本、安全。
  • docs/ontology-pack-spec.md：manifest、目录、install/upgrade、校验规则。
  • ontology/core.v0.json：8–12 个上层类型，标 draft。
  • 048_graph_*.sql + .pg.sql；test_db_pool.py v47→48。
  • 10 万边基准脚本。

验收：空 Pack 可 validate；3 跳邻居 SQLite p95 < 100ms；PG 同用例通过。

M1 · MiniApp 业务图谱

第 3–5 周

目标：跑通第一个端到端垂直切片。

  • infra/graph/ 内核：ontology、service、query、extract/app_rows。
  • MiniApp reference → 节点 / 边；写后 / 查询时派生。
  • api/routers/graph.py + Dashboard 关系 Tab。
  • graph.enabled 默认关；关闭时行为不变。

验收：三表应用自动出图；2 跳查询带证据；ACL/PII 测试通过；make all 绿。

M2 · 知识库 GraphRAG

第 6–9 周

目标：让非结构化文档变成可查询的图。

  • graph_extract job：parse/chunk → LLM 抽取 → 本体校验 → 入图。
  • 实体消歧：alias + 向量 + LLM 裁决 + 人工复核。
  • 混合检索：向量召回 → 实体链接 → 1–2 跳扩展 → 重排 → 引用。
  • 20–30 条多跳问答评测集。

验收：多跳问答相对纯向量提升 ≥10–15%；引用准确率不降；关闭图时回退纯向量。

M3 · 主动 Agent L0/L1

第 10–12 周

目标：先做“只读观察 + 建议”，不写数据。

  • Trigger Registry：cron / 外部事件 / app schedule / data_version / webhook。
  • 三个 watchdog：数据质量、退款异常、合同到期。
  • 每日 / 每周摘要 + 通知 + 建议账本。
  • 反馈按钮：有用 / 无用 / 稍后 / 不再提醒。

验收：每天 1 份摘要；告警准确率 > 80%；零写入；每用户每日告警数可控。

M4 · 动作 Copilot L2

第 13–16 周

目标：Agent 准备动作，人审批后执行。

  • Action types：approve_refund / publish_video / create_followup_task。
  • 前置条件 + 幂等键 + HITL + 审计 + 结果验收。
  • 动作建议卡（MiniApp / IM / 通知）。

验收：建议接受率 > 40%；零未审批写入；动作可回滚 / 可追溯。

M5 · Pack 产品化

第 17–20 周

目标：第二个项目只写 Pack 和映射，不改内核。

  • 第二个参考 Pack（合同审查或客户跟进）。
  • Pack install / upgrade / uninstall + dry-run + 兼容检查。
  • 专家 manifest / MiniApp 模板挂载 ontology_pack。
  • Pack 作者指南 + 升级指南。

验收：第二个 Pack 对内核改动 < 10%；两个 Pack 的能力问题通过；安装 / 升级 / 回滚可审计。

M6 · 低风险自治 L3（条件触发）

M4 之后

前置：预算闸门、kill switch、无人值守 HITL、Verifier、异常收件箱。

只在这些都就绪后做：自动补别名、重建图、发提醒等可逆动作；每动作预算 / 频率上限；失败自动回滚 / 升级。

9. 产品化与多项目复用

产品化顺序：L0 项目定制 → L1 内核复用 → L2 Pack 规范 → L3 市场 / 认证。不要先做市场；等 3–5 个真实 Pack 和外部作者需求后再做。

10. 指标与治理

指标

类别 指标
图质量 3 跳 p95、孤儿率、重复实体率、覆盖率
AI 质量 抽取准确率 / 召回率、Query DSL 正确率、引用准确率、幻觉率
主动质量 告警准确率、建议接受率、动作成功率、误报率、每用户每日告警数
成本 单文档抽取 token、单问题延迟、每活跃用户成本
产品化 新项目接入时间、复用类型比例、Pack 安装 / 升级成功率

治理

  • ACL / PII：图查询按源资源 ACL 过滤；属性级 PII 标记；公开链接不暴露图。
  • HITL：删除、低置信合并、业务动作走审批；MANDATORY_HITL_TOOLS 不可绕过。
  • 预算：按 Agent / 用户 / 项目归集 token；超限暂停 + 通知。
  • 频率 / 免打扰：复用主动关怀的 active hours、随机频控、去重。
  • 版本：Pack SemVer；内核兼容范围；破坏性变更 + 迁移。
  • 审计：本体变更、图重建、动作执行、Pack 安装 / 升级全部进 audit_log。
  • 评测：每个 Pack 至少 20 条能力问题；CI 不通过不允许发布。

防骚扰

  • 相关性评分：规则 + LLM 打分，低于阈值不打扰。
  • 分级交付：紧急即时通知；普通日报 / 周报；低优先级进看板。
  • “为什么现在告诉我”：每条主动消息带触发原因 + 证据 + 影响。
  • 反馈按钮：有用 / 无用 / 稍后 / 不再提醒；反馈进 memory。
  • 每用户每日告警上限；mute 率可观测。

11. 风险与不做

最大风险

  1. 本体过度设计，业务不用。
  2. 抽取质量差，图变垃圾场。
  3. 主动 Agent 变骚扰，用户关掉。
  4. 没有证据，回答不可信。
  5. 没有预算，成本失控。
  6. 没有 HITL，动作越权。

明确不做

  • 万能本体 / 50+ 类型（等 2–3 个项目再抽）。
  • 第一版做 Pack 市场 / 计费 / 认证。
  • OWL 推理机 / SPARQL 端点（需要时导出 RDF）。
  • 默认引入 Neo4j（先用关系库 + 递归 CTE）。
  • 自动静默合并实体。
  • 让 LLM 直接写 SQL / 做聚合 / 决定权限。
  • 每个事件都唤醒 LLM。
  • 没有预算 / HITL / kill switch 就做自治。
  • 先做多 Agent 再单 Agent。
  • 把多租户塞进当前单实例架构。

12. 决策点

1. 第一个垂直切片选哪个？

MiniApp 业务图谱 / 知识库 GraphRAG / 主动 watchdog。

建议：MiniApp 业务图谱。数据已结构化、边确定、价值可见。

2. 图的范围怎么定？

每个应用 / Agent 一个 graph_id，还是团队共享？

建议：默认按项目隔离，显式共享；跨项目图必须走 ACL。

3. 部署形态：SQLite 单机优先，还是 PG 优先？

建议：双栈同 schema，SQLite 先跑基准，PG 用同一组用例做 parity。

4. 主动性目标：第一版只做 L0/L1，还是直接 L2？

建议：L0/L1 先跑 2–4 周，测准确率再进 L2。

5. 是否改 octop-memory 上游补类型化关系？

建议：先做 Octop 侧关联层，不改上游；等记忆图谱成为核心需求再推动。

附录 A：数据模型（DDL 草图）

仅示意，正式实现按 AGENTS.md §7 的资源表约定：整数 id + 公开字符串 id，子表 FK 引用公开字符串；SQLite / PG 各一份迁移。

CREATE TABLE graph_ontologies (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  graph_id TEXT NOT NULL UNIQUE,
  owner_user_id INTEGER NOT NULL,
  agent_id TEXT,
  name TEXT NOT NULL,
  schema_json TEXT NOT NULL,
  version INTEGER NOT NULL DEFAULT 1,
  status TEXT NOT NULL DEFAULT 'draft',
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE TABLE graph_nodes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  node_id TEXT NOT NULL UNIQUE,
  graph_id TEXT NOT NULL REFERENCES graph_ontologies(graph_id) ON DELETE CASCADE,
  node_type TEXT NOT NULL,
  canonical_name TEXT NOT NULL,
  normalized_name TEXT NOT NULL,
  properties_json TEXT NOT NULL DEFAULT '{}',
  confidence REAL NOT NULL DEFAULT 1.0,
  status TEXT NOT NULL DEFAULT 'active',
  source_kind TEXT NOT NULL,
  source_ref TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
CREATE INDEX idx_graph_nodes_lookup
  ON graph_nodes(graph_id, node_type, normalized_name);

CREATE TABLE graph_edges (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  edge_id TEXT NOT NULL UNIQUE,
  graph_id TEXT NOT NULL REFERENCES graph_ontologies(graph_id) ON DELETE CASCADE,
  edge_type TEXT NOT NULL,
  src_node_id TEXT NOT NULL,
  dst_node_id TEXT NOT NULL,
  properties_json TEXT NOT NULL DEFAULT '{}',
  confidence REAL NOT NULL DEFAULT 1.0,
  status TEXT NOT NULL DEFAULT 'active',
  source_kind TEXT NOT NULL,
  source_ref TEXT NOT NULL,
  valid_from INTEGER,
  valid_to INTEGER,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
CREATE INDEX idx_graph_edges_out
  ON graph_edges(graph_id, src_node_id, edge_type);
CREATE INDEX idx_graph_edges_in
  ON graph_edges(graph_id, dst_node_id, edge_type);

CREATE TABLE graph_aliases (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  alias_id TEXT NOT NULL UNIQUE,
  graph_id TEXT NOT NULL,
  node_id TEXT NOT NULL,
  alias TEXT NOT NULL,
  normalized_alias TEXT NOT NULL,
  source TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
CREATE INDEX idx_graph_aliases_lookup
  ON graph_aliases(graph_id, normalized_alias);

CREATE TABLE graph_sources (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  source_id TEXT NOT NULL UNIQUE,
  graph_id TEXT NOT NULL,
  kind TEXT NOT NULL,
  ref TEXT NOT NULL,
  source_hash TEXT NOT NULL DEFAULT '',
  last_synced_at INTEGER,
  status TEXT NOT NULL DEFAULT 'pending',
  error TEXT NOT NULL DEFAULT ''
);

附录 D：术语表

术语 含义
Ontology对象类型、关系类型、动作类型、属性约束组成的可执行契约。
知识图谱（KG）按本体约束存储的节点、边、属性、别名与证据。
LPGLabeled Property Graph，带标签和属性的属性图；与 RDF 三元组相对。
GraphRAG用图结构增强检索：实体链接、图扩展、证据重排、带引用回答。
Pack可安装/升级的本体包：类型、映射、动作、问题、UI 配置。
Provenance节点/边的来源与证据：源表行、知识库 chunk、置信度、时间。
Query DSL受本体约束的结构化查询描述，由 LLM 生成、后端校验并编译执行。
HITLHuman-in-the-loop，关键动作需人工审批。
L0–L4主动性分级：观察、建议、审批执行、低风险自动、自治。
Walking Skeleton走通全链路的最小垂直切片，用来验证架构而不是堆功能。
